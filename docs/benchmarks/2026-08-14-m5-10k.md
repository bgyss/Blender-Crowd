Populations: 959 S1 agents over 15,877,210 agent-ticks; 9,041 S2 agents over

The heading-reversal counter keeps a deliberately loose declared tolerance. It
fires on alternating signed corrections above 0.001 rad, so it measures
micro-corrections rather than visible jitter; the abrupt-turn rate carries the
tight bar. Both stay reported either way.

The thresholds are a bar, not a restatement of this run. The rejected

background tier stalled, 0.216 m peak overlap — fails three of them, and
`m5_gate::tests::the_rejected_fixed_lane_candidate_fails_these_thresholds`
replays it through the same file to keep that true.

## Gate item 3 — tier transitions

`crates/crowd-core/tests/m5_tier_transitions.rs`, six tests, all passing. A
camera sweep drives repeated promotions and demotions across a 240-agent
city-flow population over 900 ticks; a guard test requires the fixture to
produce more than 100 transitions so the rest cannot pass vacuously.

- Stable IDs never change and slots are never reassigned.
- No agent's route handle changes across a transition, so layer composition
  survives.
- The largest single-tick displacement on a transition tick stays under 0.5 m:
  a transition changes how often an agent is solved, never where it is.
- An agent still braking after a transition keeps its accumulated stall ticks.
  The property is stated carefully: `stall_ticks` legitimately returns to zero
  when an agent stops braking, so only a drop *while still braking* is a fault.
- Render tier always follows the committed simulation tier.

## Gate item 4 — camera/focus animation scheduling

Presentation classification is now scheduled by tier: S0/S1 every tick, S2 on
the stable-ID-staggered two-tick cadence, S3 every eighth tick. Clip phase
still advances every tick for every agent from actual root displacement, so a
background agent whose clip choice is stale does not slide.

Measured saving at 10K: S2 evaluated 50.0% of its classifications, S1 100%.
`animation_scheduling_changes_evaluation_cost_not_root_motion` runs the same
declared mix with scheduling on and off and requires every agent's position,
yaw, and velocity to agree **bitwise** — presentation scheduling has no path
into integration, so any difference at all is a contract violation rather than
a tolerance question.

## Gate item 5 — CPU fallback

`crates/crowd-core/tests/m5_cpu_fallback.rs`, six tests, all passing. No GPU
backend is implemented, so this proves two things:

1. Requesting `metal`, `cuda`, or `vulkan` degrades to `cpu_reference` with a
   recorded reason naming the backend that could not be provided, and the
   resulting kernel agrees with the reference bitwise.
2. The comparison harness a future GPU backend must pass actually
   discriminates. A second CPU implementation using a pairwise reduction tree —
   the same class of difference a GPU work-group reduction introduces — agrees
   within the declared tolerance while **not** being bitwise identical
   (max error 2.4e-7 m/s against a 1e-3 m/s tolerance). A backend drifting
   0.01 m/s is rejected, and one that moves agents between cells is rejected
   regardless of tolerance, because density is a meaning difference rather than
   a precision one.

The [backend support matrix](../backend-support-matrix.md) is unchanged: only
`cpu_reference` is implemented.

| Render tier histogram (present agents) | R1 128 / R2 1,072 / R0 0 |
| Bake | 13.39 s for 5,000 ticks |

- The cache baked at the declared `m5_background_10_90` profile carried it: an
  89.3% background share of the agents present, and zero agents drawn at
  full-character R0. An undeclared profile name is refused rather than silently
  defaulted.
- Attaching a 10,000-agent cache added **one** persistent scene object, and the
  whole population lives as point attributes on it. This is the procedural
  property the 100K gate turns on, and it is asserted rather than assumed.
- Instance count is compared against the agents actually present at the tick,
  not the whole population: the reference concourse emits over time, so 8,800
  of the 10,000 are not yet placed at the inspected frame. Anchoring to the
  population would assert the emission schedule rather than that playback
  stayed procedural.
- The scale and profiling panel populated from the measured report and its gate
  adjudication: measured headline, `PASS (26 checks)`, named bottleneck ("steer
  phase, 81.0% of measured phase time"), and per-tier animation scheduling
  ("S1: 100% of classifications evaluated; S2: 50%"). Estimates live in a
  separate box, are labelled "(estimate)", and running the preflight estimator
  leaves the measured fields untouched — asserted, because an estimate that
  reads as a result is worse than no estimate.
- A report predating per-tier metrics is refused with an explanation rather
  than partially displayed.

The same runner passes at its 1,000-agent default, where 700 of 1,000 agents
are present at the inspected tick and render in 0.53 s.

## What this report does not establish

State these limits with any headline drawn from this report.

- **No GPU backend exists.** No Metal, CUDA, or Vulkan execution, performance,
  or cross-vendor parity claim follows from this run.
- **Peak allocator bytes are not resident memory.** The memory budget is
  recorded from the counting allocator, not measured RSS.
- **The UI gate's artist task is not run here.** The M5 UI gate asks an artist
  to configure the mix, identify an injected bottleneck, cancel and resume a
  long operation, and explain the active fallback from the interface. The panel
  now carries the information that task needs, but the task itself — with
  responsiveness, time on task, and screenshots — has not been conducted.
- **Cancellation and resume are proved for the cache matrix, not the UI.** The
  62.6 ms cancellation probe is a cache-layer measurement.
- **This is the 10K gate only.** The 100K gate is a separate report against the
  same threshold file, and must additionally prove streaming and procedural
  extraction do not expand 100,000 characters into Blender scene objects.
